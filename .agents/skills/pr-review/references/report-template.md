## 1. レビュー結果

冒頭に、ラベル別の件数と指摘対象の観点を `must`、`question`、`suggestion`、`nitpick` の順で示す。

```markdown
**[must] 2件**

- F-01 / 認可・セキュリティ: 権限を確認せず更新できる
- F-02 / テストの妥当性: 主要な異常系が未検証

**[question] 1件**

- F-03 / 仕様・業務ルール整合性: 無効化済み利用者の扱いが不明

**[suggestion] 0件**

**[nitpick] 0件**
```

- 件数は観点表にある各ラベルの指摘数と一致させる。
- 1件以上のラベルだけ、`指摘ID / 主観点: 指摘の短い題名` を箇条書きにする。
- 0件のラベルは件数だけ表示し、`なし` の箇条書きを追加しない。
- `[must]` は `must (blocking)`、`[question]` は `question (blocking)`、`[suggestion]` は `suggestion (non-blocking)`、`[nitpick]` は `nitpick (non-blocking)` に対応する。
- `APPROVE`や`REQUEST_CHANGES`など、実行していないGitHub actionを示す語は使わない。

固定15観点と指摘を次の1表へ統合する。15行は名称・順序・粒度を変えず、問題がある行の `指摘` セルへID、ラベル、重大度、要約、影響を記載する。

- 1つの指摘が複数観点に関係しても、主観点の1行だけへ記載する。他の行では根拠として関連を説明しても指摘IDを重複させない。
- `問題あり` には `must`、`suggestion`、`nitpick` のいずれかの指摘を付ける。merge判断に影響する `要確認` には `question (blocking)` を付ける。
- `問題なし` は確認した対象と根拠を書く。`対象外` は理由を書く。

## 2. 指摘詳細

観点表に記載したすべての指摘をID順に詳述する。指摘がなければ `なし` と書く。

```markdown
### F-01: 指摘の短い題名

- **【must】（blocking）：中**
- **要求ID:** R-001 / なし
- **対象:** `path/to/file:line`
- **指摘:** 発生条件、現在の処理、期待される処理
- **影響:** 利用者、データ、セキュリティ、運用に生じる実害
- **根拠:** 仕様、呼び出し経路、test、CIなどの確認内容
- **修正方針:** 問題を解消する最小限の対応
```

表の要約をそのまま繰り返さず、発生条件、期待動作、実害、根拠、修正方針を補足する。

表示上のラベルは次の形式へ統一する。分類・判定時の内部名は `severity-and-labels.md` のまま維持する。

| 内部分類 | 出力表示 |
| --- | --- |
| `must (blocking)` | `【must】（blocking）：大/中/小` |
| `question (blocking)` | `【question】（blocking）：大/中/小` |
| `suggestion (non-blocking)` | `【suggestion】（non-blocking）：大/中/小` |
| `nitpick (non-blocking)` | `【nitpick】（non-blocking）：小` |

- ラベル・blocking区分・重大度は1つの太字行として最初に置く。
- 指摘、影響、根拠、修正方針を同じ行へ詰め込まず、項目ごとに改行する。
- ID、ラベル、重要な結論は太字、path・SHA・要求IDはcode表記を使い、装飾目的の記号を増やしすぎない。

## 3. 要求との対応

実装の妥当性を判断するために使った要求と、その実装・テスト結果を簡潔に示す。情報を取得・統合したという作業説明は書かない。BacklogやGitHub Issueは、要求または指摘の根拠として必要な箇所だけ参照する。

| 要求 | 判定 | 実装・テスト根拠 | 指摘 |
| --- | --- | --- | --- |
| **R-001**<br>検証可能な要求<br>仕様: PR / GitHub Issue / Backlog課題・comment ID | 実装済み / 未実装 / 部分実装 / 要確認 / 対象外 | `path/to/file:line`、`path/to/test:line` / なし | F-01 / なし |

要求表の `F-xx -> R-xxx` と指摘詳細の `R-xxx -> F-xx` は双方向で一致させる。仕様根拠が複数ある場合も、取得経路や取得件数ではなく、判断に使った箇所だけを書く。

## 4. 確認範囲・未確認事項

```markdown
- **対象:** `OWNER/REPO#123`
- **比較:** `base-ref` (`base SHA`) -> `head-ref` (`head SHA`)
- **主な確認箇所:** changed files、関連する既存実装・設定・docs
- **検証:** CI/check、実行済みtestと結果
- **未確認事項:** 取得できないpatch、未実行test、仕様上の不明点、残リスク / なし
```

Backlog取得がpartial、truncated、失敗の場合は、レビュー判断に影響する未確認範囲だけを `未確認事項` に記載する。正常に取得・統合できたこと自体は記載しない。

## 5. 変更概要

PRまたは差分で実際に変更された内容を2-4項目で簡潔に記載する。課題情報を取得した、複数情報源を統合した、15観点で確認した、というレビュー手順は含めない。

## 出力前の整合性検証

- 観点表が固定15観点を名称・順序どおり1行ずつ含む。
- ラベル別サマリーの件数、指摘ID、主観点が観点表と一致する。
- 指摘IDと要求IDがそれぞれ一意である。
- 観点表に存在しない指摘IDを、指摘詳細や要求表で参照していない。
- 要求表に存在しない要求IDを、指摘詳細で参照していない。
- 指摘詳細の `F-xx -> R-xxx` と要求表の `R-xxx -> F-xx` が双方向で一致する。
- `問題あり` の観点に指摘があり、merge判断に影響する `要確認` に `question (blocking)` がある。
- `未実装`、`部分実装`、merge判断に影響する `要確認` の要求に、指摘IDまたは指摘不要の理由がある。
- 内部処理の説明ではなく、レビュー結果、根拠、対応方針が中心になっている。
