# PRレビュー結果テンプレート

チャットのプレビューとGitHub review bodyで、次の6セクションを順番どおり使う。プレースホルダーは実際の内容へ置き換える。

## 1. レビュー指摘

| ID | ラベル | 重大度 | 要求ID | レビュー観点 | 対象 | 指摘内容 | 影響 | 根拠 | 修正方針 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| F-01 | `must (blocking)` / `question (blocking)` / `suggestion (non-blocking)` / `nitpick (non-blocking)` | 大 / 中 / 小 | R-001 / なし | 必須15観点のうち主となる1項目 | `path/to/file:line` | 発生条件を含む問題の要約 | 利用者・データ・運用に起きる実害 | PR、Backlog、code flow、test、CI | 最小限の対応方針 |

指摘がない場合は表を空行で埋めず、`指摘事項なし` と書く。

### 指摘詳細

指摘ごとに、inline commentだけでは伝わらない場合に限り補足する。

```markdown
#### F-01: 指摘の短い題名

発生条件、現在の処理、期待される処理、影響、根拠、修正方針を簡潔に記載する。
```

## 2. 課題・対応内容と処理の流れ

### 情報源

| 情報源 | 対象 | 把握した内容 |
| --- | --- | --- |
| GitHub PR / GitHub Issue / Backlog課題 / Backlogコメント・変更履歴 / 親子課題 | PR番号、Issue番号、Backlog課題キー、comment ID | 課題、要求、対応内容、仕様変更、未確定事項 |

### 課題と対応内容

| 項目 | 内容 | 根拠 |
| --- | --- | --- |
| 解決したい課題 | 誰のどの問題を解決するか | PRまたは課題情報 |
| PRの対応内容 | PRが何を変更したと説明しているか | PR本文 |
| 受け入れ条件 | 完了と判断できる条件 | GitHub IssueまたはBacklog |
| 対象外・制約 | 今回扱わない範囲、技術・運用制約 | 情報源 |
| 矛盾・未確定 | 情報源間で一致しない内容 | 情報源 |

### 要求トレーサビリティ

| 要求ID | 要求 | 仕様根拠 | 実装根拠 | テスト根拠 | 判定 | 指摘ID |
| --- | --- | --- | --- | --- | --- | --- |
| R-001 | 検証可能な要求 | PR / GitHub Issue / Backlog課題キー / comment ID | `path/to/file:line` / なし | `path/to/test:line` / なし | 実装済み / 未実装 / 部分実装 / 要確認 / 対象外 | F-01 / なし |

指摘表と要求トレーサビリティ表の参照は双方向で一致させる。例えば指摘表で `F-01` の要求IDを `R-001, R-002` とした場合、要求表の `R-001` と `R-002` の指摘IDにも `F-01` を含める。

### 処理の流れ

```text
Entry point
  -> handler / component / module
    -> service / repository / API client / infrastructure
      -> DB / external service / rendered UI / deployed resource
```

## 4. 確認した関連箇所

| 種別 | 対象 | 確認理由・結果 |
| --- | --- | --- |
| GitHub / Backend / Frontend / DB / Infra / Docs / Test / CI | repository、PR、ref、SHA、file、check | 呼び出し元、契約、設定、検証などの確認内容 |

GitHub PRではrepositoryとPR番号、base/head refとSHA、changed files、既存review、CI/checksを含める。Backlogを確認した場合は課題キー、取得したコメント・変更履歴・親子課題、確認理由を含める。

## 5. 未確定事項・追加で欲しい情報

- 仕様上の不明点、取得できないpatch、未実行test、確認できない外部依存、残リスクを書く。
- 追加確認が不要なら `なし` と書く。

## 6. 変更概要

- PRまたは差分の目的と主要変更を3-5行で記載する。

## Inline commentテンプレート

差分上の正確な変更行へ紐付けられる指摘だけ、次の形式でinline commentにする。review bodyの指摘表からは省略しない。

```markdown
**must (blocking) / 重大度: 中 / F-01 / バリデーションの妥当性**

空の`name`も保存できるため、この入力で一覧画面の表示が崩れます。

根拠: request validationでは長さ上限だけを確認しており、必須判定がありません。

修正方針: trim後の空文字を拒否し、この境界値のtestを追加してください。
```

複数ファイルにまたがる問題、差分外が主対象の問題、CIやtest全体の不足、正確な行を確定できない問題はreview bodyだけに記載する。

## 出力前の整合性検証

- 指摘IDと要求IDがそれぞれ一意である。
- 指摘表に存在しない指摘IDを、要求表や15観点表で参照していない。
- 要求表に存在しない要求IDを、指摘表で参照していない。
- 指摘表の `F-xx -> R-xxx` と要求表の `R-xxx -> F-xx` が双方向で一致する。
- `問題あり` の観点に、対応する指摘IDがある。
- `未実装`、`部分実装`、merge判断に影響する `要確認` の要求に、指摘IDまたは指摘不要の理由がある。
