# 課題コンテキスト作成フロー

コードレビュー前に、PRが解決しようとしている課題と、実装が満たすべき要求を確定する。情報源を混ぜて要約せず、出所を保持したまま統合する。

## 1. 情報源を整理する

| 情報源 | 主に読み取る内容 | 注意点 |
| --- | --- | --- |
| PR title・body | PRの目的、対応内容、変更範囲、確認方法、対象外 | 実装者の説明であり、課題仕様そのものとは限らない |
| GitHub Issue・discussion | 背景、受け入れ条件、合意事項、未解決事項 | 古い記述と最新合意を区別する |
| Backlog課題本文 | 業務上の課題、要求、受け入れ条件、制約 | コメントや変更履歴で後から変更されている可能性がある |
| Backlogコメント | 追加要求、質問、回答、合意事項、作業記録 | 最新コメントや発言者だけを理由に確定仕様と扱わない |
| Backlog変更履歴 | 説明、状態、担当者などの変更内容 | 状態・担当変更だけを仕様変更と誤認しない |
| 親課題・子課題 | 対象範囲、依存関係、先行条件 | 親子関係だけで全内容を今回の要求に含めない |
| code・test・docs | 実際に実装された内容と検証範囲 | codeを仕様の根拠として仕様不足を正当化しない |

## 2. 課題コンテキストを作る

次を、根拠となる情報源と一緒に整理する。

- 解決したい課題
- 対象利用者または対象処理
- 期待される正常系の動作
- 異常系、境界値、権限、状態遷移
- 受け入れ条件
- 技術・運用上の制約
- 明示された対象外
- PRが説明している対応内容
- 未確定事項と情報源間の矛盾

PR本文と課題情報をそのまま連結するのではなく、「課題として求められていること」と「PRが対応したと説明していること」を分離する。

## 3. 仕様変更と矛盾を扱う

- 更新日時が新しいだけで確定仕様と判断しない。コメントが明確な決定、承認、変更指示かを読む。
- コメントまたは変更履歴で明示的に変更された要求は、元の記述を削除せず `置換済み` として関係を残す。
- PR本文とBacklogが異なる場合は、PR本文でBacklog要求が上書きされたと推測しない。
- Backlog課題内で矛盾する場合も勝手に優先順位を決めない。
- merge判断に影響する矛盾は要求を `要確認` とし、`question (blocking)` の候補にする。

## 4. 要求へ分解する

1つの行をコードまたはtestで判定できる粒度にし、`R-001`から連番を付ける。

| 要求ID | 要求 | 種別 | 根拠 | 状態 |
| --- | --- | --- | --- | --- |
| R-001 | 誰が、どの条件で、何をできるか | 正常系 / 異常系 / 権限 / データ / UI / 運用 / 対象外 | PR本文、GitHub Issue、Backlog課題キー、comment ID | 有効 / 置換済み / 要確認 |

複数の振る舞いを1行にまとめない。曖昧な要求を実装都合で具体化しない。

## 5. 実装と突合する

| 要求ID | 実装根拠 | テスト根拠 | 判定 | 指摘ID |
| --- | --- | --- | --- | --- |
| R-001 | `path/to/file:line` | `path/to/test:line` / なし | 実装済み / 未実装 / 部分実装 / 要確認 / 対象外 | F-01 / なし |

- 要求がコード、test、設定、docsのどこで満たされるか確認する。
- 実装が見つからなければ、単に差分にないのか、既存実装で満たされるのかを周辺コードで確認する。
- PRに要求外の変更があれば、意図された変更か、不要なscope拡大かを確認する。

## 6. 対応関係を検証する

- 指摘表に書いた要求IDが、要求トレーサビリティ表に存在することを確認する。
- 指摘 `F-xx` が要求 `R-xxx` を根拠にする場合、指摘表側の要求IDと要求表側の指摘IDへ同じ組み合わせを記載する。
- 要求表で `未実装` または `部分実装` とした行に指摘IDがない場合、指摘不要と判断した理由を未確定事項へ記載する。
- `実装済み` の要求を問題の直接根拠として指摘へ紐付けない。別の不足要求または15観点上の問題へ分ける。
- 要求に直接対応しないセキュリティ、性能、保守性などの指摘は、要求IDを `なし` とする。
