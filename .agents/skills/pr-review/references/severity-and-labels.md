# ラベルと重大度

各指摘へ、対応方針を示すラベルと、実害の大きさを示す重大度の両方を付ける。ラベルと重大度は別の軸として判定する。

## ラベル

| ラベル | 使用条件 | コメントで求めること |
| --- | --- | --- |
| `must (blocking)` | コード、仕様、セキュリティ、データ整合性などに根拠のある問題があり、merge前の対応が必要 | 修正または、問題が成立しないことを示す根拠 |
| `question (blocking)` | 仕様や前提が曖昧・矛盾しており、回答なしでは実装の妥当性やmerge可否を判断できない | 仕様の回答と、必要に応じた実装・testの更新 |
| `suggestion (non-blocking)` | 現状でも要求を満たすが、保守性、性能、運用性などに具体的な改善効果がある | 任意の改善検討。見送ってもmergeを妨げない |
| `nitpick (non-blocking)` | 命名、表記、局所的な読みやすさなど、ごく軽微な改善 | 任意の微修正。必ずnon-blocking |

`blocking` はPRの準備状態を示すラベルであり、GitHubの `REQUEST_CHANGES` actionを自動で選ぶ指示ではない。

単なる質問はレビュー指摘にしない。回答によって実装変更の要否が変わる具体的な不確定事項だけを `question (blocking)` にする。好みだけの提案、実害や改善効果を説明できないnitpickは記載しない。

## 重大度

| 重大度 | 基準 | 代表例 |
| --- | --- | --- |
| 大 | mergeやリリースを止めるべき影響。主要機能停止、認証・認可回避、機密情報露出、データ消失・越境、復旧困難な本番障害 | 認可漏れ、secret混入、破壊的migration、主要APIの常時失敗 |
| 中 | 利用者や運用に明確な実害があるが、条件や範囲が限定される、回避策がある、または復旧可能 | 一部入力で誤動作、error時の不整合、現実的な性能劣化、重要分岐のtest gap |
| 小 | 現在の機能・セキュリティ・データ整合性を壊さない局所的な問題 | 軽微なUI/docsずれ、限定的な保守性低下、誤解を招く表記 |

## 判定手順

1. 問題が起きる入力、状態、操作、環境を特定する。
2. 壊れる挙動、データ、権限、運用を特定する。
3. 到達可能性、影響範囲、回避策、復旧可能性を確認する。
4. 根拠から到達可能な最も深刻な影響で重大度を決める。
5. 明確な問題なら `must`、仕様回答が必要なら `question`、任意改善なら `suggestion` または `nitpick` を選ぶ。

修正工数や確度を理由に重大度を上下させない。`question` は、問題となる前提が成立した場合の影響で重大度を付ける。通常、`must` と `question` は大または中、`nitpick` は小とする。
